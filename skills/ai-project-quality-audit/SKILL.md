# AI 项目质量审计

对单个目标项目执行证据优先的质量审计。评判对象是交付的软件项目，而不是所用模型、Prompt 或 AI 代码占比。

## 边界

- 一次只审计一个项目目录。用户给出多个目录时，要求其选择一个，或拆成独立审计。
- 默认只读审计：不得修改被审计项目、补写测试、伪造报告或修复问题。用户明确要求修复时，另行进入代码修改流程。
- 不把「能启动」「Demo 跑通」「测试覆盖率高」或任一工具分数当作项目合格的充分条件。
- 所有结论必须对应可复查证据：文件与行号、实际命令及结果、测试报告、扫描报告、运行日志或人工验收记录。
- 证据不足时使用「未验证」或「需人工」，不得推断为通过。

## 开始前

1. 确认目标项目绝对路径、目标运行环境，以及预期用途或上线风险等级。
2. 读取项目规则、README、构建配置、测试配置、部署配置和已有需求／设计文档。
3. 记录基线：当前 Git 提交与工作区状态、可用运行命令、依赖锁定文件、可复现环境所需变量。
4. 若没有明确需求或验收标准，仍可做代码与运行质量审计，但必须将「需求与业务价值」标为「未验证」，并说明缺少的材料。
5. 先确定每项验证命令，再执行。命令失败时保留原始错误和退出码；不得换成更宽松的命令后宣称通过。

## 审计维度

逐项评估下表。每项至少记录「结论、证据、风险、后续动作」。

| 维度 | 必查问题 | 优先证据 |
| --- | --- | --- |
| 需求与业务价值 | 需求、功能和验收用例是否可追溯？核心问题是否被解决？ | 需求文档、验收用例、用户验收记录 |
| 功能正确性 | 主流程、异常、边界、权限和数据状态是否正确？ | 单元、集成、端到端测试及人工复现 |
| 安全与合规 | 是否有鉴权、输入校验、密钥、依赖漏洞、越权或许可证风险？ | SAST、依赖／密钥扫描、权限测试、许可证清单 |
| 可靠性与韧性 | 失败、重试、并发、超时、断网和依赖不可用时是否可控？ | 故障注入、恢复演练、日志、错误率与恢复记录 |
| 性能与容量 | 目标负载下的延迟、吞吐和资源占用是否达标？ | 压测报告、容量边界、性能基线 |
| 可维护性 | 模块边界、可读性、测试、文档、构建和发布是否可接手？ | Code Review、静态分析、构建复现、维护文档 |
| 用户体验与无障碍 | 用户能否完成关键任务？键盘和辅助技术是否可用？ | 可用性测试、关键任务记录、无障碍检查 |
| 交付与运维 | 是否可部署、观测、回滚和排障？ | CI/CD、配置管理、日志指标、告警、Runbook、回滚演练 |

## AI 特有风险检查

在上述维度之外，必须单列以下检查；每项均需实际证据：

1. **虚构能力**：验证第三方包、导入、API、配置项和服务能力确实存在且版本兼容。
2. **假接线**：追踪页面、路由、接口、数据层、权限与测试之间的调用链，识别占位实现、未注册组件或永不执行的测试。
3. **理想路径偏差**：检查测试是否覆盖无效输入、空数据、权限不足、失败响应和边界值，而非只验证 AI 生成的示例流程。
4. **来源与许可证**：检查依赖、复制代码、示例和素材的许可证、归属及敏感信息。
5. **可复现交付**：在干净环境按文档复现安装、构建、测试、数据库迁移与启动；记录环境变量与外部前置条件。

## 验收判定

先判定一票否决项，再判定上线门槛，最后才给分数。

### 一票否决

下列任一项成立时，结论为「不通过」：

- 核心需求未满足，或需求无从验证而项目声称已可上线；
- 存在未接受的高危安全漏洞、数据丢失风险或越权风险；
- 无法从干净环境构建或部署；
- 没有可验证的回滚或数据恢复方案；
- 关键运行、测试或扫描证据被伪造、缺失或相互矛盾。

### 上线门槛

未命中一票否决后，确认：关键用户流程通过；关键接口具备自动化测试；高风险安全问题已处理或有明确接受记录；性能满足目标；日志、监控、告警与排障／回滚资料存在且可验证。

无法满足的条目必须列为「阻塞上线」或「风险接受」，由用户或项目负责人决定；审计者不得代为接受风险。

### 可选评分卡

仅在用户需要排序、比较或跟踪改进时使用。每一分都必须链接证据，且不覆盖一票否决结论。

| 维度 | 权重 |
| --- | ---: |
| 需求达成 | 30 |
| 功能正确性与测试 | 20 |
| 安全与数据保护 | 15 |
| 可靠性、性能与运维 | 15 |
| 可维护性 | 10 |
| 用户体验与无障碍 | 10 |

## 工具使用原则

- 优先运行项目已有的构建、测试、Lint、SAST、依赖扫描、性能测试和部署验证命令。
- SonarQube、CodeQL、SAST、覆盖率和扫描器只提供某些维度的证据；不得把工具绿灯表述为项目整体通过。
- 需要新增工具时，先说明它覆盖的维度、运行条件和盲区，再执行；不安装或上传代码到外部服务，除非用户授权。
- UI 项目需要实际检查关键交互、控制台错误、响应式与无障碍；后端项目需要检查 API 契约、权限、错误语义与数据一致性。

## 输出格式

使用以下结构，先给结论，后给证据：

```markdown
# 项目质量审计：<项目名>

## 结论
- 判定：通过 / 有条件通过 / 不通过 / 证据不足
- 一票否决：无 / <具体项>
- 上线阻塞项：<列表或无>
- 未验证项：<列表或无>

## 维度结果
| 维度 | 结论 | 证据 | 风险与后续动作 |
| --- | --- | --- | --- |

## AI 特有风险
| 检查项 | 结论 | 证据 | 风险 |
| --- | --- | --- | --- |

## 实际执行
| 命令或操作 | 结果 | 证据位置 |
| --- | --- | --- |

## 可选评分
- 总分：<n>/100；仅作比较，不替代上线门槛。
```

结论用语必须区分「已验证」「部分验证」「未验证」和「需人工」。列出真实命令、退出码和报告路径；不要用概括性赞语替代证据。
